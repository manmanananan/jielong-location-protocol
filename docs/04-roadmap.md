### 1.4 踩坑两则

**① `title` 被误改**

第一版把 `title` 放进 `NAME_KEYS`，结果把表单单元格的**字段标签**
（「定位」「姓名」）全改成了地点名，服务端收到的表单定义直接变形。

修法：`title` 只在 `location` / `locationData` / `clockLocationInfo` / `poi`
这类定位上下文里才改写，由 `in_loc` 标志控制（见 `src/jl_addon.py`
的 `LOC_CTX_KEYS` / `_deep_rewrite`）。

**教训**：小程序里同名 key 在不同层级含义不同，按名字全局匹配一定会踩到。

**② 同秒抓包互相覆盖**

`sign_body_<时间戳>.json` 的时间戳只到秒。连点两次签到、或前端重试时，
两次请求落在同一秒，后一条直接覆盖前一条——**看起来有存证，实际丢了一条**。
这类 bug 在排障时最容易误导人（会以为「只有一次请求」）。

修法：落盘前查重名，冲突就加 `_1` / `_2` 后缀。

**教训**：凡是「按时间命名产物」的地方，都要假设同一时间点会有多条。

### 1.5 `status:0` 的四种出现情形（反直觉，实测）

```powershell
# ① 404 的响应体也是 status:0
curl.exe -s -X POST "https://jielong.huolieyun.com/activity/nope" -d "{}"
# {"msg":"","status":0}          HTTP 404

# ② 根路径
curl.exe -s "https://jielong.huolieyun.com/"
# {"msg":null,"status":0}        HTTP 200

# ③ 方法不对
curl.exe -s "https://jielong.huolieyun.com/activity/activityDetail"
# {"msg":"哎哟！出错啦！","status":0}   HTTP 200

# ④ 历史记录
# base.txt: {"msg":"","status":0}
```

四种情形**没有一个是业务成功**。结论：`status:0` = 默认值，不是成功码。
判定成功必须同时看 HTTP 码 + `msg` + 有无 `data`，并等 U1 解开后定标准
（见 §二 U4）。

## 五、教训：同一个值，多种语义

> 这一节记的是本项目的**方法论**，不是具体 bug。
> 它比「要小心」有用，因为它能照着做。

### 5.1 发生了什么

`status:0` 被写进 README 时，依据是 `base.txt` 里一条
`{"msg":"","status":0}` 的记录，加上「0 通常是成功码」这个直觉。
两处都站不住：

- `base.txt` 只是一条**来源不明**的文本，不知道是谁、在什么场景下产生的；
- 「0 = 成功」是**跨系统的惯例**，不是这个系统的契约。

后来用 curl 打线上，`status:0` 出现在四种互不相同的情形里（见 §1.4），
**没有一个是业务成功**。它不是「失败码写错了」，而是**从一开始就没有
「成功码」这个语义**——0 只是字段的默认值。

### 5.2 真正的判据：找语义单一的字段

这次能纠正，靠的不是「更小心地看」，而是换了个问法：

> 不是问「0 是不是成功？」——这个问题有歧义，怎么答都可能对。
> 而是问「**哪个字段只在一种情况下取某个值？**」

按这个问法重扫一遍响应体，答案是 `msg`：

| 字段 | 取值 → 语义 | 是否单一 |
|---|---|---|
| `status` | `0` → 可能是 404 / 根路径 / 方法错 / 真的成功 | ❌ 多对一 |
| `status` | `901` → 缺鉴权 | ✅ 目前唯一单一 |
| `msg` | `"token为空"` → 缺鉴权 | ✅ 单一 |
| `msg` | `"哎哟！出错啦！"` → 方法不对 | ✅ 单一 |
| `msg` | `""` → **无信息**（404 和未知情况都是空） | ❌ 空值不承载语义 |

**这就是「多对一」陷阱**：多个不同的原因映射到同一个值。
遇到这种字段，无论它叫 `status`、`code` 还是 `errcode`，都不能当判据。

### 5.3 怎么识别自己踩进去了

三个信号，中一个就要停手重查：

1. **一个值对应多种情形**：`0` 同时出现在 404、根路径、方法错里。
   这时候它不是「码」，是「没赋值」。
2. **字段与文案互相矛盾**：`msg` 说「出错啦」，`status` 说 0。
   矛盾的双方至少有一个不是判据。
3. **只能举出一个正面例子，且来源不明**：`base.txt` 就是这种。
   **孤证不算证据**，尤其当它来自「不知道哪来的一个文件」时。

### 5.4 反过来的用法：找阴性对照

这次真正的转折点是**主动去打一个不存在的路径**：

```powershell
curl.exe -s -X POST ".../activity/nope" -d "{}"
# {"msg":"","status":0}      ← 404 也是 0
```

如果不打这一条，只看「真接口返回 901」「其它接口也返回 901」，
会得到「一切正常」的错觉——因为**缺了阴性对照，就没有比较基准**。

所以探测协议时的固定动作应该是：

```
① 一个已知存在的目标 → 记录它的响应
② 一个已知不存在的目标 → 记录它的响应
③ 一个已知参数错误的目标 → 记录它的响应
④ 三者取差集，只有「只在 ① 出现」的字段/取值才是判据
```

§3.3 的「901 当路径探针」就是这么得出的：901 只在真实路径出现，
404 路径上永远没有——**这个字段的语义是单一的，所以能当判据。**

### 5.5 落到文档规则上

- 写「X 表示 Y」之前，先问：**X 还有没有别的来源？**
- 举不出**阴性对照**的结论，标 `⚠️`，不要写进「已验证」。
- 孤证（一条来源不明的记录、一次偶然观察）不能升级为事实。
- 已经写错的，**改它并留痕**（本文 §四 保留了错误结论的原文与纠正过程，
  §1.4 保留了四种情形的实测对照），不要静默删掉——下一个人需要知道
  这里曾经错过，才不会又踩回去。
