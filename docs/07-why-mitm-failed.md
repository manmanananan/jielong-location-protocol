# 07 · 反代为什么失败：域名级代理豁免

> **状态：❌ 已证伪。** 这不是「改了没用」，是「压根抓不到」。
>
> 保留这份记录的理由：**「为什么抓不到包」本身就是一个结论**。
> 它解释了为什么最终必须绕到客户端注入（`docs/06`），
> 也省得下一个人再花一整晚去查 CA、查证书固定、查 mitmproxy 配置。

---

## 0. 结论先行

| 问题 | 答案 |
|---|---|
| WMPF 走不走系统代理？ | **走**。`servicewechat.com` / `wxs.qq.com` / `apis.map.qq.com` 全部经过 8899 |
| 那为什么抓不到接龙？ | `jielong.huolieyun.com` 被**域名级豁免**，直连 |
| 是证书固定吗？ | **不是**。连 TLS 握手都没发生 |
| 是配置错了吗？ | **不是**。同一时刻别的域名都抓到了 |
| 能绕过吗？ | 未尝试成功。理论上要驱动层/驱动级重定向，成本远超收益 |

## 1. 曾经确认成立的部分

代理链路本身是**对的**，这一点必须说清楚，否则会误导人往配置方向查。

抓包可见这些域名的请求正常经过 8899：

```
servicewechat.com    CONNECT [pass]
wxs.qq.com           CONNECT [pass]
apis.map.qq.com      CONNECT [pass]
```

`[pass]` 是 mitmproxy 的标记，表示连接已建立并进入代理处理流程。
**说明：系统代理设置生效、CA 信任正确、mitmproxy 工作正常。**

---

## 2. 关键发现：54 : 0

在同一个时间窗内（约 25 秒），同时做两件事：

### 2.1 抓这个域名的直连

```powershell
# 目标 IP（DNS 解析所得）
Resolve-DnsName jielong.huolieyun.com -Type A
# → 39.104.28.144

# 统计到该 IP 的连接
Get-NetTCPConnection -RemoteAddress "39.104.28.144"
```

结果：**25 秒内出现 54 条到 `39.104.28.144:443` 的连接，全部为直连，
没有一条经过 8899。**

### 2.2 核查微信进程的全部连接

```powershell
Get-NetTCPConnection -State Established |
  Where-Object { $_.OwningProcess -in (Get-Process WeChatAppEx).Id }
```

结果：**6 条 Established，全部指向 8899；非 8899 的为 0 条。**

### 2.3 两条数据放在一起

这看起来矛盾——「微信的连接全在 8899」和「54 条直连不在 8899」怎么可能同时成立？

答案：**那 54 条连接不属于 `WeChatAppEx.exe`。**

```powershell
# 查 54 条连接到底属于谁
Get-NetTCPConnection -RemoteAddress "39.104.28.144" |
  Select-Object OwningProcess -Unique |
  ForEach-Object { Get-Process -Id $_.OwningProcess | Select-Object Id, ProcessName }
```

结论指向微信的**另一个进程**（网络服务进程），而不是渲染小程序的 `WeChatAppEx.exe`。

**这才是真正的机制**：

```
微信小程序 (WeChatAppEx.exe / WMPF)
   │  发起 https://jielong.huolieyun.com/activity/sign
   ▼
微信网络服务进程  ←──────── 这里读到了「豁免名单」
   │
   ├─ 在名单里 → 直接建 TCP（绕过 WinINET 代理设置）
   └─ 不在名单 → 走系统代理 127.0.0.1:8899
   │
   ▼
39.104.28.144:443
```

**代理设置在 `WeChatAppEx.exe` 这一层是生效的**（所以它自己的连接都在 8899），
但真正的 HTTP 请求被**转交给网络服务进程**发出，而那个进程对
`jielong.huolieyun.com` 做了直连豁免。

## 3. 这个精度很重要：别写成别的

排查过程中出现过几个**错误结论**，都写在这里，免得后人重复：

| 错误说法 | 为什么错 | 正确说法 |
|---|---|---|
| 「WMPF 不读 WinINET 代理」 | 它读了。`servicewechat.com` 就是走代理的 | 读，但**特定域名被豁免** |
| 「mitmproxy 没配对 / 端口错」 | 配置对，同期别的域名全抓到了 | 配置正确，问题在客户端侧 |
| 「有证书固定（pinning）」 | 是**根本没到 TLS 阶段**，连握手都没发生 | 不是 pinning，是连接不走代理 |
| 「微信进程的连接全在代理上，所以肯定抓到了」 | 只看了 `WeChatAppEx.exe`，漏了真正发包的进程 | 要按**目标 IP** 查，不要只按进程查 |

### 3.1 为什么「证书固定」这个猜测特别有迷惑性

因为它的现象和「抓不到」很像：都是没有明文。

但两者有一个**决定性的区别**：

| | 证书固定 | 域名豁免 |
|---|---|---|
| TCP 连接经过代理吗 | **经过** | **不经过** |
| mitmproxy 日志 | 有 CONNECT，然后 TLS 失败 | **什么都没有** |
| 能不能看到 SNI | 能 | 看不到 |
| 排查手段 | 看 mitmproxy 的 TLS 错误 | 看 `Get-NetTCPConnection` 的直连 |

**判据：如果 mitmproxy 连 CONNECT 记录都没有，那就不是证书问题，
是连接根本没来。** 这一条能省掉大量时间。

## 4. 排查顺序（下次照这个走）

如果你怀疑「代理抓不到某个域名」，按这个顺序，不要跳步：

```
① 别的域名能抓到吗？
   ├─ 不能  → 代理/CA/系统设置问题，查 docs/03
   └─ 能    → 继续

② mitmproxy 有该域名的 CONNECT 记录吗？
   ├─ 有，然后 TLS failed → 证书固定，查 pinning 绕过
   └─ 完全没有            → 继续（大概率是豁免）

③ 按目标 IP 查所有连接
   Get-NetTCPConnection -RemoteAddress "<TARGET_IP>"
   ├─ 有连接，本地端口不在代理端口 → 豁免确认
   └─ 无连接                      → 请求根本没发出（前端就没发）

④ 查这些连接属于哪个进程
   → 如果不是你预期的进程，说明请求被转交了
```

**第 ③ 步是关键**：不要只查「微信进程的连接」，
要按**目标 IP** 查——因为真正发包的可能是另一个进程。

---

## 5. 能绕过吗

没试成功。理论上三条路，成本都远超收益：

| 思路 | 难度 | 说明 |
|---|---|---|
| 驱动层拦截（WFP / TDI） | 极高 | 需要内核驱动，且要处理 TLS |
| Hosts 改指向本地 | 中 | 但服务端证书校验会失败；且改 hosts 影响全局 |
| 在微信网络进程里 hook | 高 | 需要另找注入点，稳定性差 |

对比一下：**`docs/06` 的 CDP 注入一次就成功了。**
所以这里没有再深入——不是做不到，是不值得。

> 这也是工程判断的一部分：**知道什么时候停止深挖**。
> 54:0 的数据已经足够定性，继续投入的边际收益是负的。

---

## 6. 这个负结果的价值

1. **它排除了整条路线**，让人不必再怀疑「是不是我配置错了」。
2. **它给出了一个可复用的判据**：`mitmproxy 无 CONNECT 记录` + `按目标 IP 能查到直连` = 豁免，不是证书问题。
3. **它解释了 54:0 这个反直觉数据**：微信的代理设置在渲染进程生效，
   但真正的 HTTP 由网络服务进程发出，那个进程有豁免名单。
4. **它把方案推向正确答案**：正因为抓不到，才回头用 CDP。
