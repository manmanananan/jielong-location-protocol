## 2. 已知缺陷（重点章节）

> 这一节是本文存在的**主要理由**。兜底工具的坑必须写在显眼处，
> 否则下一个人会以为它是「稳定方案」。

### 2.1 端口漂移

- [ ] 现象：工具每次启动监听的端口不固定（<PORT_A> / <PORT_B> / 随机）
- [ ] 触发条件：上次进程未退干净、端口被占、或工具自身的端口分配策略
- [ ] 后果：脚本里写死的端口失效，调用方连不上
- [ ] 规避：启动后先探测实际端口，不要硬编码
- [ ] 是否可根治：待确认（如果工具支持 `--port` 参数就能）

### 2.2 白名单不含新端口

- [ ] 现象：端口变了，但对端（小程序/微信）的白名单仍只认旧端口
- [ ] 原因：白名单是静态配置，工具启动时不重新协商
- [ ] 后果：连接被拒，表现为「工具在跑但没反应」——**与「没启动」难以区分**
- [ ] 规避：启动顺序（先改配置再启动）、或手工同步白名单
- [ ] 排障判据：查工具侧有无 listening、对端有无 outgoing 拒绝

### 2.3 跑完小程序崩溃

- [ ] 现象：签到完成后小程序页面白屏 / 微信进程退出 / 需重启微信
- [ ] 触发时机：工具执行完毕、连接断开的那一刻
- [ ] 可能原因：待查（连接未优雅关闭？注入的脚本未清理？）
- [ ] 影响面：会不会影响**同一次会话里的其它小程序**（待确认）
- [ ] 数据风险：崩溃前签到是否已落库（待确认，关键）
- [ ] 规避：跑完手动等 N 秒再操作、或直接重启微信

## 附：写这一节时的注意事项

1. **不要把兜底写成推荐。** 它是兜底，先天的稳定性就差。
2. **§2 必须比 §5 长。** 复现步骤谁都能写，坑只有踩过的人知道。
3. **崩溃类问题要写清「数据有没有落库」**——这是使用者最关心的，
   也是「崩了要不要重跑」的判断依据。
4. **端口类问题要给排障判据**，不能只写「端口可能变」。
   要写「怎么确认它变没变」。
